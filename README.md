# 云效消息监听服务（feishu-merge-relay）

一句话：**替合并项目接住云效推送的消息，先写进磁盘，再慢慢转发过去。** 这样合并项目重启的那几十秒里，云效推来的合并请求不会丢，起来之后自动补发。

它是 [feishu-merge-bot](https://github.com/yst199324/feishu-merge-bot)（下称"合并项目"）的**可选前置服务**。合并项目自己也能直接接云效推送，只是重启窗口会丢消息；加了这个服务，那几十秒就补上了。

**它不解析报文、不调云效接口、不发飞书卡片、不连飞书长连接。** 只有三件事：验签、写文件、转发。因此它没有云效令牌、没有飞书应用密钥、没有群号，要填的只有两项，重启只要三秒，也几乎不需要跟着业务改动。

## 一、它到底解决什么问题

合并项目收到云效推送后，要依次做：查合并请求详情（两三次接口）→ 拼卡片 → 发到群里。这条链路要几秒。

重启合并项目的那二三十秒里，端口不在监听，云效推过来的请求直接连接被拒，**这条消息就没了**——云效后台不会自动重投（官方文档里没有承诺过自动重试，只有一个手工「重新投递」按钮），你也不会知道漏了哪一个。

加了这个服务之后：

```
云效 → 监听服务（写文件、立刻回 200）→ 磁盘 → 合并项目慢慢处理
```

云效看到的永远是"推送成功"，因为消息已经在磁盘上了。合并项目什么时候起来、什么时候处理完，都不影响消息本身。

**代价**：多一个进程、多一套部署目录、多一次转发（延迟增加一秒以内）。

## 二、要不要部署它

两种形态，二选一。**推荐先按形态一跑**，等真的被重启丢消息咬过一次，再上形态二。

| | 形态一：只部署合并项目 | 形态二：两个都部署 |
|---|---|---|
| 云效 Webhook 指向 | 合并项目 `18123` | 监听服务 `18123` |
| 合并项目端口 | `18123`（对外） | `18601`（**不对公网**） |
| 监听服务 | 不部署 | `18123`（对外） |
| 合并项目重启时 | **会丢**那几十秒的消息 | 不丢，起来后自动补发 |
| 云效接口抖动时 | 卡片发不出去，只能事后补 | 自动重试六次，最长跨 2 小时 38 分 |
| 要多维护的 | 无 | 一个进程 + 一个 `queue/` 目录 |

判断标准很简单：**合并项目会不会在有人提合并请求的时候重启？** 只要会（发版、改配置、服务器维护），就值得上形态二。

两种形态的切换只改端口和一行配置，见[第八章](#八把云效地址切过来)，回滚同样只改这两处。

## 三、它怎么工作

```
① 有人提合并请求
        ↓
② 云效 POST http://服务器:18123/webhook/yunxiao
        ↓
③ 监听服务做四件检查：密钥对不对、报文是不是太大、
   有没有带投递编号、这条是不是已经收过
        ↓
④ 全部通过 → 把报文原样写成一个文件 → 返回 200
        ↓
⑤ 后台线程每 2 秒看一次目录，把文件转发给合并项目的内部入口
        ↓
⑥ 合并项目返回 200 → 删文件，这条结束
   返回 400 → 永远处理不了，移进死信目录，不再重试
   返回 503 / 连不上 / 超时 → 移进重试队列，按阶梯再试
```

第 ③ 步里"这条是不是已经收过"很重要：云效有时会重投同一份报文，而文件名就是投递编号，同名文件已存在就直接返回 200、不再写一份。

**转发的报文是原始字节，一个字都不改。** 连请求头里的 `Content-Type`（含编码）也原样带过去，否则中文会乱码。三个请求头必须一起带：`X-Codeup-Token`、`X-Codeup-Delivery`、`X-Codeup-Event`——合并项目第一件事就是校验它们。

## 四、三个队列

```
<监听服务工作目录>/
  relay.jar
  application.yml
  .env
  queue/
    pending/     待发：收到了还没成功转发的
    retry/       重试：转发失败，等着下一次重试的
    dead/        死信：重试用完或永远处理不了的
    meta/        辅助：每条消息的事件名和 Content-Type（转发时要原样带回）
```

四个目录在服务启动时自动创建，权限 `700`（报文里有提交人姓名和邮箱，不能让别的用户读到）。

`meta/` 不在最初的队列设计里，是实现时补的：三个队列目录只存报文原文，而转发时必须把云效那一次的 `Content-Type`（含 charset）和事件名原样带回去，否则走监听服务这条路时中文会变乱码。它只是辅助信息，丢了也不影响转发（回落默认值），所以它不参与限额、不做超龄，只在消息被删干净后顺手清掉。

### 4.1 文件名就是全部状态

| 目录 | 文件名 | 举例 |
|---|---|---|
| `pending/` | `{投递编号}_{首次到达毫秒}.json` | `a1b2c3d4-0001_1763604612000.json` |
| `retry/` | `{投递编号}_{首次到达毫秒}_{已试次数}.json` | `a1b2c3d4-0001_1763604612000_3.json` |
| `dead/` | `{投递编号}_{首次到达毫秒}_{进死信时间}_{原因}.json` | `a1b2c3d4-0001_1763604612000_20261120093012_auth.json` |

- **投递编号**来自云效请求头 `X-Codeup-Delivery`，入队时固化进文件名，之后一直不变。重试时原样带回，合并项目才能认出"这是同一条消息"，不会重复发卡。
- **首次到达毫秒**是这条消息进队列的时间，跨三个目录都不变。判断"谁最老""超过寿命没有"都看它。
- **文件的修改时间**只表示"什么时候可以动它"：在 `retry/` 里就是下一次该重试的时刻。所以**判断年龄不能看修改时间**，只看文件名。

### 4.2 上限与寿命

| 队列 | 默认上限 | 默认寿命 | 超限怎么办 | 超寿命怎么办 |
|---|---|---|---|---|
| `pending/` | 50 条 | 3 小时 | 删最早进来的，记警告日志 | 移进 `dead/`，记警告日志 |
| `retry/` | 50 条 | 3 小时（和待发共用一个寿命） | 删最早进来的，记警告日志 | 移进 `dead/`，记警告日志 |
| `dead/` | 500 条 | 7 天 | 删最早进死信的，记警告日志 | 直接删文件，记警告日志 |

寿命从"云效推过来的那一刻"开始算，**转进重试队列不清零**。所以最坏情况也在 3 小时内收口——不会出现"在队列里躺两天，恢复后突然刷出一堆早就没用的审批卡"。

> 3 小时这个值不能随便调小：重试阶梯加满累计 2 小时 38 分，寿命如果只有 2 小时，最后一档重试永远跑不到就被判超龄了。

### 4.3 重试阶梯

| 第几次重试 | 等多久 | 累计 | 打算覆盖什么 |
|---|---|---|---|
| 1 | 5 秒 | 5 秒 | 单次网络抖动 |
| 2 | 30 秒 | 35 秒 | 合并项目重启（起停约 20 秒） |
| 3 | 2 分钟 | 2 分 35 秒 | 云效接口短时 5xx、网关换节点 |
| 4 | 5 分钟 | 7 分 35 秒 | 持续抖动、发版窗口 |
| 5 | 30 分钟 | 37 分 35 秒 | 需要人介入才能恢复的故障 |
| 6 | 2 小时 | 2 小时 37 分 35 秒 | 人不在（午休、开会、夜里） |

六次都失败 → 移进 `dead/`，打错误日志。

阶梯就是一个配置列表（`delay-seconds`），**列表里有几个数就是重试几次**。想加一档就加一个数，不用改代码。

> **第 5 档为什么正好是 30 分钟**：合并项目处理一条投递前会先"占坑"，坑记 30 分钟，
> 同一条投递重复投过去**不会**延长这个时间。所以万一它拿了坑就卡死（进程还活着、那条线程不动了），
> 前面几档重试只会一直得到"处理中"，只有等这 30 分钟过期后再推一次，才会被当成全新投递真正重做一遍。
>
> 把阶梯改短（比如只留前 4 档）之后，表面现象只是"重试都失败了、进了死信"，
> 实际是这条消息从头到尾**一次都没有被真正重做**，很难看出根因在阶梯长度。
> `RelayPropertiesTest` 里有一条测试专门守着这件事，改阶梯改到跨不过 30 分钟就会直接报错。

### 4.4 哪些情况不重试

有些失败重试一万次也没用，直接进死信，不在队列里耗着：

| 情况 | 处理 |
|---|---|
| 报文解析不了、取不到仓库号或合并请求号 | 死信，原因标记 `bad` |
| 云效令牌失效（合并项目返回 400 并说明是凭据问题） | 死信，原因标记 `auth`，日志单独提示换令牌 |
| 合并项目内部入口返回 404 / 405（开关没开） | 死信，日志直接写"内部入口没开，请检查 INTERNAL_ENDPOINT" |
| 在队列里超过 3 小时 | 死信，原因标记 `expired` |
| 六次重试都失败 | 死信，原因标记 `exhausted` |

其余一律重试：连不上、读超时、500 / 502 / 503 / 504、发卡失败。

## 五、开工前先确认这五件事

| # | 要确认 | 怎么确认 |
|---|---|---|
| 1 | `18123` 端口能对外 | 手机切 4G 访问 `http://服务器IP:18123/webhook/yunxiao`，返回 405 就算通 |
| 2 | 合并项目已经退到 `18601` | 改它的 `.env`：`SERVER_PORT=18601` |
| 3 | 合并项目的内部入口已经打开 | 改它的 `.env`：`INTERNAL_ENDPOINT=true`，然后重启 |
| 4 | 两边的 Webhook 密钥一样 | 监听服务的 `.env` 和合并项目的 `.env` 里 `YUNXIAO_WEBHOOK_TOKEN` 填同一个值 |
| 5 | 部署目录够用 | 默认最多 100 条待发 + 500 条死信，报文限 2 MB，留 2 GB 余量足够 |

**第 3 项最容易漏。** 漏了的表现是：监听服务日志写"转发失败，返回 404"，每条消息重试六次、跨两个半小时才进死信，看起来像网络问题。服务启动时会主动探一次目标地址，探测不通会直接在启动日志里打 ERROR，不用等第一条消息进来才发现。

**合并项目的 `server.address` 不要填 `127.0.0.1`。** 现在同机部署填了也能用，但将来两个服务分机器，监听服务就连不过去了。要限制访问，从安全组和防火墙做，别从代码配置做。

## 六、编译与配置

### 6.1 拿代码并编译

```bash
git clone https://github.com/yst199324/feishu-merge-relay.git
cd feishu-merge-relay
mvn clean package
```

产物固定叫 `target/relay.jar`。

### 6.2 填 `.env`

真实值写在 `.env` 里，`application.yml` 只有占位值、可以整份覆盖到服务器——和合并项目是同一套做法。

```bash
cp .env.example .env
chmod 600 .env
```

**必填只有两项：**

| 变量 | 填什么 |
|---|---|
| `YUNXIAO_WEBHOOK_TOKEN` | 和云效后台、合并项目 `.env` 里那个**完全一致** |
| `RELAY_TARGET_URL` | 合并项目内部入口，同机就是 `http://127.0.0.1:18601/internal/yunxiao` |

其余都有默认值，一般不用动：

| 变量 | 默认 |
|---|---|
| `RELAY_SERVER_PORT` | `18123` |
| `RELAY_QUEUE_DIR` | `./queue` |
| `RELAY_MAX_AGE_MINUTES` | `180`（3 小时） |
| `RELAY_PENDING_MAX_SIZE` | `50` |
| `RELAY_RETRY_MAX_SIZE` | `50` |
| `RELAY_DEAD_MAX_AGE_DAYS` | `7` |

`.env` 已被 `.gitignore` 排除，不会进仓库。服务器上放一份这台服务器自己的，重启服务时不用重新填。

> `.env` 的位置是相对**进程工作目录**的，所以启动脚本里必须有 `cd` 到自己目录这一步。否则会静默读不到 `.env`，表现成"配置改了没生效"——这是最难查的一类问题。

### 6.3 `application.yml` 不用改

从仓库里复制一份到 jar 同级即可：

```bash
cp src/main/resources/application.yml /部署目录/relay/application.yml
```

里面没有真实值，改它也不会影响凭据。想改队列上限这类参数，改 `.env` 更省事（下次覆盖 yml 不会冲掉）。

## 七、启动与日常三条命令

部署目录里应该有这些：

```
/你的目录/relay/
├── relay.jar
├── application.yml
├── .env
├── start.sh
├── stop.sh
├── restart.sh
└── requeue-dead.sh     # 死信补发工具，不参与启停
```

第一次要加执行权限，之后只用三条命令：

```bash
chmod +x start.sh stop.sh restart.sh requeue-dead.sh

./start.sh      # 启动
./stop.sh       # 停止
./restart.sh    # 重启（换 jar、改配置都用它）
```

启动成功的标志，日志里这两行：

```
队列目录就绪：pending=0 retry=0 dead=0
Started RelayApplication in xxx seconds
```

另外要看到目标探测这一句：

```
内部入口可达：http://127.0.0.1:18601/internal/yunxiao
```

如果是 ERROR 说不通或者是 404，先去合并项目那边把 `INTERNAL_ENDPOINT=true` 打开。

**两个服务必须部署在不同目录。** 各自有 `application.yml`、`.env`、`logs/`、`*.pid`，混在一起会出现"重启一个把另一个带停""pid 文件互相覆盖"。

## 八、把云效地址切过来

### 8.1 切过去

1. 先按[第七章](#七启动与日常三条命令)把监听服务起起来，确认启动日志没有 ERROR
2. 用 `curl` 手工打一条，确认能落盘、能转发（见[第九章](#九它健康吗)）
3. 云效后台打开「代码库 → 设置 → Webhooks」
4. URL 从 `http://服务器IP:18123/webhook/yunxiao` 改成 `http://服务器IP:18123/webhook/yunxiao`——**端口不变，只是这台机器上 18123 现在归监听服务了**
5. 点一次「测试」，看监听服务日志里出现一条落盘记录

> 如果合并项目之前不在 18123，这一步就是把 URL 里的端口改成监听服务的端口，路径 `/webhook/yunxiao` 一个字都不要改。

### 8.2 回滚

1. **先让队列跑空**：把云效地址改回直连合并项目，等监听服务把 `pending/`、`retry/` 里的都转发完（`/health` 里三个数归零），再停它
2. 停监听服务：`./stop.sh`
3. 合并项目 `.env` 改回 `SERVER_PORT=18123`、`INTERNAL_ENDPOINT=false`，重启

**别先停监听服务再回滚**：`pending/` 和 `retry/` 里剩下的文件没人消费，云效也不会重投，那些消息就直接丢了。实在来不及等，把文件逐个用 `curl` 打到合并项目的 `/webhook/yunxiao`（带上 `X-Codeup-Token` 和 `X-Codeup-Delivery`），确认 200 再删文件。

`dead/` 里的文件不受影响，本来就是人工处理，7 天内可以补发。

## 九、它健康吗

服务自己提供了一个只读接口：

```bash
curl http://127.0.0.1:18123/health
```

它告诉你四件事：

| 看什么 | 正常什么样 | 不正常说明什么 |
|---|---|---|
| 三个队列各有多少条 | `pending` 和 `retry` 都是 0 或个位数 | `pending` 一直涨 = 转发不通；`retry` 一直涨 = 下游持续失败 |
| 最老的一条进来多久了 | 不超过几分钟 | 超过半小时说明堵住了 |
| 最近一次转发结果、连续失败次数 | 成功，失败次数为 0 | 连续失败 ≥ 3 就该去看日志 |
| 最后一次成功是什么时候 | 就是刚才 | 几小时前 = 转发已经坏了一段时间 |

日志在 `logs/` 下：

```bash
tail -f logs/relay-info.log      # 日常看这个
tail -f logs/relay-error.log     # 只看报错
tail -f logs/console.log         # 启动阶段输出
```

**最该盯的两个数字**：`pending/` 的条数和 `dead/` 的条数。前者涨说明转发不通，后者涨说明有东西在持续失败。

## 十、死信怎么补发

`dead/` 里的消息**不会自动重发**。它是人工待办清单——自动重发等于无限循环，而且令牌什么时候换好，机器判断不了。

文件名末尾的原因标记就是筛选用：

| 标记 | 意思 | 怎么处理 |
|---|---|---|
| `auth` | 云效令牌失效 | 先去合并项目换令牌，再把这批补发 |
| `bad` | 报文或参数有问题 | 一般补发也没用，看一眼日志再决定 |
| `exhausted` | 六次重试都失败 | 确认下游恢复后补发 |
| `expired` | 在队列里超过 3 小时 | 大概率已经被人手工处理，补发前先看一眼那个合并请求还在不在 |

**换完令牌，一句就能筛出该补的那批：**

```bash
ls -1 queue/dead/*_auth_*.json
```

补发用 `requeue-dead.sh`，一次一个文件：

```bash
./requeue-dead.sh queue/dead/a1b2c3d4-0001_1763604612000_20261120093012_auth.json
```

它只做四件事：解析出投递编号 → 生成新文件名放回 `pending/`（次数归零、原因标记去掉）→ 把修改时间设成当前 → 打印一行结果。

批量就自己写循环：

```bash
for f in queue/dead/*_auth_*.json; do ./requeue-dead.sh "$f"; done
```

补发后就是一条全新消息，重新走六次阶梯。发卡前合并项目还会重查一次云效状态，早就合并或关闭的会被拦下，不会刷废卡。

**死信保留 7 天**，过期直接删文件。7 天够发现故障、换令牌、补发；再久也没意义，而且报文里有姓名和邮箱，不该长期躺在磁盘上。

## 十一、出问题了看哪里

| 现象 | 先查什么 |
|---|---|
| 云效点「测试」，监听服务日志什么都没有 | 端口没放行或地址填错。手机切 4G 访问 `http://IP:18123/webhook/yunxiao`，返回 405 才算通 |
| 云效显示 403 | `YUNXIAO_WEBHOOK_TOKEN` 和云效后台填的不一致，一个字符都算 |
| 云效显示 400，日志写"没带 X-Codeup-Delivery" | 中间的 Nginx / 防火墙把没在白名单里声明的请求头滤掉了。检查 `proxy_set_header`，别让它吃掉未知头 |
| 日志写"内部入口返回 404" | 合并项目 `INTERNAL_ENDPOINT=true` 没开，或目标地址端口填错 |
| 日志写"转发失败，连接被拒" | 合并项目没起来，或 `RELAY_TARGET_URL` 指向的端口不对 |
| 日志写"连接失败 / 超时"，但端口是通的 | 先 `curl http://127.0.0.1:18601/internal/yunxiao`，返回 **404 就是合并项目 `INTERNAL_ENDPOINT` 没开**；再看 `RELAY_TARGET_READ_TIMEOUT_MS` 是不是偏小（默认 120 秒，合并项目最坏约 85 秒） |
| 日志写"合并项目正在处理同一条投递（IN_FLIGHT）" | **正常节流，不是故障**：合并项目正在处理这条消息，还没出结果就回 503 让我们稍后再试，文件留在 `retry/` 里按阶梯重试。只有当这类 503 持续出现且 `pending/` 一直在涨时，才说明合并项目卡住了 |
| `pending/` 一直有文件不动 | 转发线程卡住或下游一直超时。看 `retry/` 里的次数是不是在涨 |
| `retry/` 里次数一直涨 | 下游持续失败：先看合并项目日志，再看云效令牌是不是过期 |
| 卡片一直不来，但日志说转发 200 | **问题不在这个服务**。合并项目已经收下了，去它那边看（`/test/doctor`、发卡日志） |
| `dead/` 里突然多了 `_auth_` 一批 | 云效令牌失效，按[第十章](#十死信怎么补发)处理 |
| 磁盘满了 | 三个队列都有限额，正常不会涨到满。查 `dead/` 是不是被关掉了清理，或 `logs/` 没轮转 |
| 服务起来但 `/health` 里三个数都是 0，消息也不进来 | 云效地址还指着合并项目那个端口。这是没切换，不是故障 |

**一条排查顺序**：云效那边是绿的吗 → 监听服务日志有没有落盘记录 → 有没有转发记录 → 转发返回什么码 → 合并项目那边收到没有。四步就能定位是哪一段的问题。

## 十二、配置项完整说明

全部写在 `application.yml`，敏感值和常用开关可以用 `.env` 覆盖。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `server.port` | 18123 | 对外端口。`RELAY_SERVER_PORT` 可覆盖 |
| `relay.webhook-token` | 必填 | 云效 Webhook 密钥，和云效后台一致。`YUNXIAO_WEBHOOK_TOKEN` 可覆盖 |
| `relay.max-payload-bytes` | 2097152 | 报文上限，2 MB。超过直接返 413，不落盘 |
| `relay.queue-dir` | `./queue` | 队列根目录，下面自动建三个子目录 |
| `relay.scan-interval-ms` | 2000 | 每多久扫一次目录 |
| `relay.max-age-minutes` | 180 | 消息总寿命，从首次到达算，两个队列共用。**必须大于重试阶梯累计时长** |
| `relay.pending.max-size` | 50 | 待发队列上限 |
| `relay.pending.batch-per-round` | 10 | 待发线程每轮最多处理几条 |
| `relay.retry.max-size` | 50 | 重试队列上限 |
| `relay.retry.batch-per-round` | 5 | 重试线程每轮最多处理几条 |
| `relay.retry.max-pending-before-yield` | 10 | 待发积压超过这个数，重试线程本轮跳过，把额度留给新消息。**必须小于 `pending.max-size`** |
| `relay.retry.delay-seconds` | `[5, 30, 120, 300, 1800, 7200]` | 每次重试前等多少秒，几个数就是重试几次 |
| `relay.dead.max-size` | 500 | 死信目录上限 |
| `relay.dead.max-age-days` | 7 | 死信保留天数，过期删文件 |
| `relay.target.url` | `http://127.0.0.1:18601/internal/yunxiao` | 合并项目内部入口 |
| `relay.target.connect-timeout-ms` | 3000 | 建连接超时 |
| `relay.target.read-timeout-ms` | 120000 | 等响应超时，可用 `RELAY_TARGET_READ_TIMEOUT_MS` 覆盖。合并项目同步调用最多 3 次云效接口再发一次卡片，最坏约 85 秒，所以默认给 120 秒；调大只影响"判定失败"的早晚，不影响正确性 |
| `relay.target.threads` | 1 | 转发线程数。默认 1 保证按到达顺序；调大后不再保序 |

```
│   ├── ConfigSanityChecker.java 启动检查配置之间的矛盾（寿命 vs 阶梯、让路阈值 vs 上限）
│   └── StartupReporter.java     启动时把队列目录、三个目录条数打到日志
├── web/
│   ├── WebhookController.java   接住云效推送：验签、查大小、查编号、查重、落盘
│   └── HealthController.java    /health：三个队列条数、最老一条多久、最近转发情况
├── queue/
│   ├── QueueDirectories.java    目录建在哪、怎么列举、按什么排序（排序规则集中在这里）
│   ├── QueueStore.java          队列门面：入队、改名、换目录、删除、计数
│   ├── QueueFileName.java       三个目录的文件名规则与解析（就这一处）
│   ├── QueueHousekeeping.java   限额淘汰、超龄、死信保留期、孤儿元数据清理
│   └── MetaStore.java           事件名与 Content-Type 的读写
├── worker/
│   ├── AbstractWorker.java      消费线程模板：起线程、固定延迟、异常兜底、优雅停止
│   ├── PendingWorker.java       待发线程：扫 pending → 转发 → 删文件 / 进重试
│   ├── RetryWorker.java         重试线程：扫到期文件 → 转发 → 删文件 / 次数加一 / 进死信
│   ├── ForwardingService.java   "读报文 → 转发 → 记统计 → 打日志"，两个线程共用
│   ├── QueueOutcomeHandler.java 结论 → 队列动作（删 / 进重试 / 进死信），唯一实现处
│   ├── QueueJanitor.java        定时跑 Housekeeping
│   └── WorkerStarter.java       应用就绪后才启动线程（避免起了一半就转发）
├── client/
│   ├── RelayClient.java         转发用的 HTTP 客户端（JDK 自带，超时可配）
│   ├── StatusCodePolicy.java    返回码白名单 → 四类结论
│   ├── CredentialFailureDetector.java  400 里是不是"凭据失效"
│   └── RelayTarget.java         转发接口（worker 依赖它，不依赖具体实现，便于测试）
└── support/
    ├── RetryLadder.java         重试阶梯（配置里几个数就重试几次）
    ├── TargetProbe.java         启动时探一次目标地址，404 直接报错
    ├── RelayStats.java          最近转发结果 / 连续失败次数 / 最后成功时间
    ├── DeliveryIds.java         投递编号清洗（防目录穿越）
    └── HeaderNames.java         请求头常量（X-Codeup-Delivery 这个名字不能改）
```

**读代码的顺序建议**：`QueueFileName`（文件名就是全部状态，看懂它就看懂一半）→ `QueueStore` → `WebhookController`（入口）→ `AbstractWorker` 和两个 Worker（消费）→ `RelayClient` + `StatusCodePolicy`（返回码怎么归类）。

## 十四、几条要知道的边界

- **它只保证不丢，不保证不重复。** 转发成功但删文件前崩溃，重启后会再转发一次。合并项目按投递编号去重，第二次通常直接返回 200；万一去重记录刚好过期，群里会多一张一样的审批卡，不影响合并结果。
- **它自己也重启的那三秒，云效的请求会被拒，那条会丢。** 比合并项目二十秒的窗口小一个数量级，而且它不跟业务变化、几乎不用重启，所以不处理。要彻底封死只能上反向代理层，不值得。
- **只能起一个实例。** 两个实例各写各的文件、各自判重，同一条消息会被转发两次。要做高可用得先改判重方式。
- **不校验报文内容。** 它不懂云效报文结构，只认三个请求头。报文是不是合法、是不是合并请求事件，都是合并项目判断的。
- **绑死了云效。** 判重、转发的请求头都用云效的约定。将来换平台要改的只有这一个项目——这正是把它独立出来的原因，改这里不会碰到合并项目里的云效调用、飞书卡片、审批流程。
- **依赖本地磁盘。** 磁盘写不进去时返回 500，让云效看到投递失败——这是唯一正确的行为，不能假装成功。
- **报文里有个人信息（提交人姓名、邮箱）。** 所以队列目录权限 `700`、文件 `600`，死信只留 7 天。
